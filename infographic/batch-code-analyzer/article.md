# Batch Code Analyzer 批量文本分析

当你只想弄懂三五个文件时，把代码逐个贴给 AI 就够了。

但仓库一大，事情很快就失控：要不要分析这份文件？提示词是否一致？这次到底用了哪个模型？某个请求失败后，重试的是哪一份？结果又保存在哪里？

**Batch Code Analyzer** 想解决的，正是这段从“偶尔问一次 AI”到“稳定处理一整个代码仓库”之间的空白。

它是一个运行在 Windows、macOS、Linux 上的本地桌面工具：登记本地仓库，筛选待分析文件，批量调用兼容 OpenAI Responses API 的模型，然后把每个文件的 Markdown 结果、Token、耗时、错误和重试历史保存下来。

## 批量，不是把一堆文件塞进一次请求

先用一幅更日常的画面理解它。

夏天摘桃子，左边的人一次摘一颗：伸手、放进筐里、再伸手。右边的设备有十个独立采摘爪，同一时刻摘十颗桃子，每一颗仍然落到自己的格位里。

Batch Code Analyzer 的批量分析就是右边这件事。

你一次选定一批文件，并为它们设好统一的提示词、模型和重试策略；系统随后在设定的并发上限内，为每个文件发起**独立请求**。文件不会被拼成一段超长内容，也不会共享一份模糊的回答。每个文件都有自己的结果、耗时、失败原因和重试记录。

这带来的不只是“快一点”。更重要的是，不必再反复复制提示词、切换模型、等待上一份文件结束后才处理下一份。一次配置，整批推进；每一份结果又能单独检查。

## 一条从仓库到结果的本地流水线

一次正式分析，大致经历四步。

**先筛选。** 工具会按 `.gitignore`、文件类型、大小和安全规则扫描本地仓库。无关文件、大文件、常见密钥文件和疑似敏感内容不会在毫无提示的情况下送给模型。

**再补全上下文。** 只看一个文件，AI 很容易停留在语法层面。工具可以读取仓库中的 `README`、`AGENTS.md` 等资料，生成项目上下文摘要，让模型更有机会说明这个文件为什么存在、与谁协作、会影响什么。

**然后创建 Run。** Run 可以理解为这一批分析的“任务单”。创建后，文件清单、文件哈希、提示词、模型、上下文版本、API 路由和重试策略都会被固定下来。运行中改了项目设置，不会悄悄影响已经开始的这一批。

**最后逐份执行并归档。** 每个文件独立得到 Markdown 结果；结果和任务元数据按 Run 隔离写入输出目录，之后可以继续查看、筛选、重试或导出。

## 为什么不是写个循环调 API 就够了？

![exec-33520d9f-c6dc-4744-87c8-2a83ddfb2a21](https://fxyimg001.oss-cn-shanghai.aliyuncs.com/img/202607271417260.png)

真正难的地方，往往发生在第 20 个、第 200 个文件之后。

某个请求失败时，不能只显示一句“出错了”。你需要知道它用了哪个 API 档案、哪个模型、是否经过了备用档案切换、等了多久、还能不能安全重试。

因此，Batch Code Analyzer 把一次运行拆成三个层次：

- **Run**：一整批正式分析，以及它不可变的配置快照；
- **Task**：Run 中某一个文件的分析任务；
- **Attempt**：Task 实际发出的一次请求。

自动重试、主备切换和人工重试都会新增 Attempt，而不是覆盖旧记录。即使应用异常退出，结果未知的请求也不会被系统擅自重发，是否重新排队由用户决定。

这意味着你看到的不只是“成功”或“失败”，而是一条可解释的处理轨迹。

## 本地代码，应该有本地工具的边界

批量处理代码时，效率不能建立在放松安全边界之上。

在这个项目里，React 负责界面和交互；仓库扫描、文件读取、路径校验、模型请求和状态变更都由 Rust 完成。SQLite 是运行状态的权威来源，API Key 则交给系统的安全存储能力管理。

几个底线很明确：API Key 不进入普通配置、SQLite 明文字段、日志、错误信息或导出文件；输入输出路径要经过仓库边界、符号链接和路径逃逸检查；模型返回的内容不能触发本地命令或改写源码。

工具也不会修改、格式化或覆盖你的源代码。它的职责是理解、记录和组织分析结果，不是替你直接改代码。

## 适合哪些场景？

它特别适合这些工作：

1. 接手陌生项目时，快速获得文件职责、数据流和模块关系的第一版地图。
2. 用统一模板批量提取接口、依赖、风险、技术债或测试建议。
3. 给遗留系统建立逐文件的解释档案，方便后续检索与交接。
4. 对失败项单独重试，对已经完成的结果保留完整历史。

它不承诺模型一定正确，也不替代代码审查。它提供的是一套更可靠的工作方式：把大量文件的 AI 分析，从临时对话变成可配置、可并行、可回溯的本地流程。

## 获取与发布

项目通过 GitHub Actions 构建三平台安装包：Windows 提供 `.msi` 和 `.exe`，macOS 提供 Intel 与 Apple Silicon `.dmg`，Linux 提供 `.AppImage` 和 `.deb`。

当前发布流程尚未配置代码签名，因此首次打开时，macOS 可能需要在“隐私与安全性”中确认，Windows 也可能显示 SmartScreen 提示。
