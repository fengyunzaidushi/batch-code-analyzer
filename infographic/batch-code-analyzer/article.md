# 你不需要再一遍遍打开文件：Batch Code Analyzer 把批量代码分析做成了一个本地工作流

> 公众号文章草稿｜配图建议：`infographic.png`

当一个仓库只有几十个文件时，逐个交给 AI 分析还算轻松。文件一多，问题就变成了另一种问题：

- 哪些文件真的值得分析？
- 每个文件是不是用了同一套标准？
- 这次请求到底用了什么提示词、模型和上下文？
- 失败后重试，会不会把历史结果覆盖掉？
- 本地代码和 API Key，谁来保证不会被误发、误存、误写？

Batch Code Analyzer 的出发点，就是把这些重复而容易失控的事情，收拢成一个本地桌面工作流。

它不修改你的源代码，也不试图“猜测程序员当时是怎么写出来的”。它做的事情更具体：扫描文件、构造请求、调用模型、保存结果、管理运行记录。

## 一、它分析的是“一个仓库”，不是一段孤立代码

很多代码分析工具的问题，不是模型不会解释语法，而是它不知道当前文件在项目里的位置。

一个 `service` 文件为什么存在？它和哪些模块协作？它的输入从哪里来，输出又会影响什么？如果只把文件正文扔给模型，得到的结果往往停留在“逐行复述”。

Batch Code Analyzer 把项目上下文作为正式能力：导入或重新扫描项目时，它可以发现仓库根目录下的 `README`、`README.*` 和 `AGENTS.md`，再把这些资料生成项目上下文摘要。单文件分析时，模型看到的不只是一个文件，还包括这个文件在仓库中的角色。

这也是默认提示词强调“职责、输入输出、协作模块和可能影响”的原因：目标不是把语法换一种说法，而是帮助你建立项目地图。

## 二、从本地仓库到 Markdown 结果，完整流程只有七步

整个产品可以概括成一条线：

**登记项目 → 扫描筛选 → 设置提示词 → 配置模型 → 创建 Run → 批量执行 → 保存结果**

第一步，登记一个本地代码仓库。工具会递归扫描目录，结合 `.gitignore`、文件类型、大小限制和安全规则，筛选出适合发送给模型的真实项目文件。

第二步，配置项目默认提示词和模型。需要更细粒度控制时，可以为单个文件设置覆盖值；需要统一调整时，又可以回到项目级设置。

第三步，创建正式 Run。这里是 Batch Code Analyzer 和“一键循环请求”之间的关键区别：Run 创建时会冻结文件清单、文件哈希、提示词、模型、上下文版本、API 路由和重试策略。

第四步，调度器按并发限制执行每个文件对应的 AI 请求。每个请求都会写入统计信息，结果以 Markdown 形式保存，并按运行批次隔离输出目录。

最后，你可以查看 Token、耗时、错误、重试和主备切换过程，也可以对失败任务进行单项或批量重试。

## 三、Run、Task、Attempt：让结果可以解释，也可以复盘

批量任务最怕的不是失败，而是失败以后没人知道发生了什么。

因此，Batch Code Analyzer 把一次运行拆成三个层次：

- **Run**：一次正式批量分析，拥有不可变的配置快照；
- **Task**：Run 中针对某个文件的一次分析任务；
- **Attempt**：Task 实际发出的一次网络请求。

自动重试、备用 API 档案切换和人工重试，都会新增 Attempt，不会覆盖旧记录。这样你看到的不只是“最后成功了”，还可以追溯：第一次请求用了哪个档案、哪个模型、耗时多久，后来为什么切换或重试。

如果应用异常退出，处理中任务会被标记为“已中断/结果未知”。系统不会擅自重发可能已经在服务端完成的请求，是否重新排队由用户决定。

这套设计的核心不是增加概念，而是保护可解释性：同一个 Run 里的结果，应该能够回答“当时到底使用了什么配置”。

## 四、为什么前端只展示，Rust 才接触文件和请求

这是一个本地桌面应用，但“本地”不等于“可以随便读写”。项目采用 Tauri 2 + React + Rust 的分层方式：

- React、Vite、TypeScript 负责界面展示和交互；
- Rust 负责仓库扫描、文件读取、路径校验、模型请求和业务状态变更；
- SQLite 保存 Run、Task、Attempt 等运行状态；
- 系统 Keychain、Credential Manager 或 Secret Service 保存 API Key；
- Provider Adapter 负责兼容 OpenAI Responses API。

前端不会直接读取仓库、SQLite 或 API Key，而是通过受控的 Tauri Command 和稳定 DTO 请求 Rust。这样做的代价是需要维护 Rust 与 TypeScript 两套工具链，但换来的是更清晰的权限边界：文件系统、安全检测和状态变更集中在一个可测试的核心层。

## 五、安全边界，是产品能力的一部分

代码分析工具天然会接触敏感内容，所以安全不能只写在文档里。

Batch Code Analyzer 默认排除常见密钥文件，并检查私钥头、常见云服务访问密钥、Bearer Token、数据库连接串和高熵疑似密钥。发现风险时，文件默认不会进入 Run；即使进入错误或日志，也只保留类型、位置和掩码，不保存命中的秘密原文。

同样的边界也应用于路径：输入和输出路径要经过仓库边界、符号链接和路径逃逸检查，输出文件还要处理 Windows 保留名和大小写冲突。

安全存储方面，API Key 不写入普通配置、SQLite 明文字段、日志、错误信息、导出文件或测试快照。开发和 CI 也使用仓库内的 Mock Provider，不调用真实收费模型 API。

## 六、它适合哪些场景？

如果你面对的是下面这些任务，它会比较有价值：

1. 给新成员快速解释一个陌生仓库的模块职责和数据流；
2. 用统一模板批量提取接口、依赖、风险或技术债；
3. 为旧项目生成注释建议、测试建议或代码审查报告；
4. 对大型仓库进行逐文件分析，并把结果按 Run 独立归档。

它不承诺模型分析必然正确，也不替你修改源代码。它更像一台“分析流水线”：把输入边界、提示词、请求历史和输出结果管理好，让模型能力能够稳定地嵌入日常工作。

## 七、跨平台发布，先把本地工具真正交付出去

项目的技术栈从第一天就按三平台设计：Windows、macOS、Linux 都在发布范围内。

- Windows 提供 `.msi` 和 NSIS `.exe`；
- macOS 提供 Intel 与 Apple Silicon `.dmg`；
- Linux 提供 `.AppImage` 和 `.deb`。

推送版本标签后，GitHub Actions 会负责构建并上传正式 Release，开发者也可以在本机运行 `pnpm tauri:build` 生成安装包。

当前发布工作流还没有配置代码签名，因此 macOS 首次打开可能需要在“隐私与安全性”中允许，Windows 可能会显示 SmartScreen 提示。这是交付现状，也应该在使用前说清楚。

## 写在最后

AI 代码分析真正难的地方，从来不只是“调用一次模型”。难的是把一个仓库拆成可控的文件集合，把上下文、提示词和模型配置固定下来，把每次请求和失败原因留下来，再把结果安全地放回本地。

Batch Code Analyzer 正在做的，就是这层工程化工作。

如果你经常需要理解陌生仓库、整理遗留代码，或者想把一次性的 AI 试验变成可重复的分析流程，可以从这个仓库开始：先登记一个项目，扫描文件，写下你的分析目标，然后让每一个结果都带着它自己的上下文和历史。
